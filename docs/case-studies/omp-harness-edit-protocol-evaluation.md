# Case study: GPT-5.6 Sol shows a narrow anchored-range efficiency opportunity

## Status

This document replaces the earlier preliminary OMP review with the completed
August 16, 2026 GPT-5.6 Sol investigation and a self-contained assignment for
the next controlled evaluation.

The investigation reached a narrower conclusion than the Stencil article's
headline:

- OMP's public Hashline evidence does not justify porting OMP, replacing
  bettercodex's exact-replacement editor, or globally prefixing every read line
  with a short hash.
- A minimal GPT-5.6 Sol prototype did show a real efficiency mechanism: for
  contiguous line-range replacement and especially deletion, the model can
  avoid reproducing old content in its edit call.
- In the repeated targeted comparison, the prototype preserved correctness and
  substantially reduced edit-payload size, output tokens, and elapsed time, but
  did not reduce aggregate total tokens because anchored reads and instructions
  increased input cost.
- The evidence is sufficient to justify evaluating a production-safe optional
  strong-snapshot range operation. It is not sufficient to ship one.

No production runtime, prompt, tool, model-facing context, fixture, test, or
product behavior changed during this investigation. All prototype source,
compiled artifacts, credentials links, temporary workspaces, and session files
created for the evaluation were removed afterward.

## Executive verdict

**Yes, narrowly:** content-anchored range editing contains a plausible
GPT-5.6 Sol harness-performance improvement for large contiguous replacements
and deletions.

**No, broadly:** the evidence does not support a complete Hashline port, making
Hashline the default edit protocol, replacing exact string replacement, adding
OMP's tool surface, or adding short hashes to every ordinary file read.

The only candidate worth another evaluation is a hybrid design in which:

1. bettercodex's current exact, atomic replacement mode remains the default;
2. the same `edit` tool optionally accepts one or more line ranges tied to a
   strong full-file snapshot;
3. anchored/numbered reads are requested only when the model needs that mode;
4. stale snapshots reject the entire edit before any write; and
5. the feature is adopted only if representative GPT-5.6 Sol evaluations show
   a correctness-preserving end-to-end performance gain.

## The recommendation to evaluate next

### Recommendation

Evaluate an optional strong-snapshot anchored range operation for large
replacements and deletions while retaining exact replacement as the default.
Reject the two-character hash, global line-prefixing, large Hashline grammar,
and complete OMP tool surface.

This recommendation is deliberately phrased as an evaluation target, not a
production decision.

## Why the original claim required skepticism

Stencil's February 12, 2026 article is titled:

> We improved 15 LLMs at coding in one afternoon. Only the harness changed.

The article reports that Hashline beat patch on 14 of 16 models, improved the
mean result over patch by approximately 15 percentage points, and reduced
output tokens by as much as 61% in one row. It describes Hashline as returning
short content hashes beside line numbers and having the model reference those
anchors for replacement, range replacement, and insertion.

Source:

- [Stencil: The Harness Problem](https://stencil.so/blog/the-harness-problem)

The underlying mechanism is credible. Reproducing old text can be expensive,
ambiguous, and mechanically brittle. A line-range operation can express a large
deletion with two anchors and an empty replacement instead of echoing the
entire deleted body.

The headline nevertheless compresses several important qualifications.

### The benchmark is an edit-expression benchmark

The fixtures were generated by taking React source files, mechanically mutating
them, describing the resulting defect in prose, and scoring whether the agent
restored the expected file after formatting. Mutation categories included
operator swaps, boolean flips, off-by-one errors, optional-chain removal,
identifier changes, guard-clause removal, and related transformations.

This isolates an important question:

> Once a model has enough information to identify a mechanical source edit,
> how reliably and efficiently can it express that edit through a given tool?

It does not directly answer broader harness questions involving:

- repository discovery;
- ambiguous product requirements;
- multi-file design;
- dependency analysis;
- regression avoidance;
- test selection and interpretation;
- long-session history;
- compaction;
- prompt caching;
- recovery from unrelated tool failures; or
- whether a feature is worth its permanent prompt and implementation cost.

A result on this benchmark should therefore be described as edit-protocol
evidence, not proof that one complete coding harness is superior.

### The result is model-dependent

The article's most relevant published Codex-family row was GPT-5.2 Codex:

| Comparison | Published result |
| --- | ---: |
| Hashline versus patch | +4.6 percentage points |
| Hashline versus exact replacement | -0.4 percentage points |
| Hashline output tokens | +26% |

That row is materially different from the largest gains on weaker or
non-Codex-tuned models. It supports the article's general lesson that tool
formats can expose or hide model capability, but it also demonstrates that the
best format is conditional on the model.

The article did not publish GPT-5.6 Sol evidence.

### “Only the edit tool changed” describes a bundle

Hashline cannot be introduced by changing only one internal write function.
The tested protocol also changes model-visible behavior around it:

- `read` output acquires line identifiers;
- the edit schema changes;
- tool instructions change;
- stale-state behavior changes;
- failure messages and recovery instructions change;
- the model must learn when it may reuse an anchor; and
- the model's input-token distribution changes because every tagged read is
  larger.

Those changes may be necessary parts of the protocol, but they are separate
causal mechanisms. An evaluation must measure the bundle actually proposed for
bettercodex rather than attributing every difference to the write applicator.

### The public benchmark artifacts are not a perfectly stable record

The OMP source was inspected at commit
[`37eee719`](https://github.com/can1357/oh-my-pi/tree/37eee71978951fccf66b21f7e3e2b74596ac9d74),
dated August 16, 2026. Historical benchmark-era source was also inspected
around February 11–15, 2026.

At historical commit
`f5a96989c2ca11106bdc88c271327aa8b2f1714f`, the checked-in GPT-5.2 Codex
reports each stated one run per task over 60 tasks:

| Historical checked-in report | Passed |
| --- | ---: |
| Hashline | 46/60, 76.7% |
| Exact replacement | 49/60, 81.7% |
| Patch | 46/60, 76.7% |

The live article currently states three runs per task and 180 tasks per run, and
its displayed GPT-5.2 deltas do not exactly reproduce the historical report
values above. This may reflect later reruns, aggregation, prompt revisions, or
article updates. The important point is not to infer misconduct; it is that a
future decision should be based on a fresh, locally controlled GPT-5.6 Sol A/B,
not on reconstructing an evolving public aggregate.

### The benchmark-era instruction cost was substantial

At the historical benchmark source inspected during this investigation, simple
word and byte counts for the model-facing edit instructions were:

| Protocol prompt | Words | Bytes |
| --- | ---: | ---: |
| Exact replacement | 222 | 1,592 |
| Patch | 440 | 3,054 |
| Hashline | 889 | 6,613 |

The Hashline prompt had to explain anchors, single-line and range variants,
insertion, atomicity, formatting preservation, stale-hash recovery, no-op
recovery, schema validation, and examples. Its prompt was approximately four
times the word count of replacement mode.

This does not make Hashline wrong. It means edit-call output savings must be
measured against permanent input cost, prompt-cache behavior, additional read
bytes, and any extra reasoning or verification the protocol induces.

### The current OMP grammar has continued to grow

By the August 16 source revision, OMP's Hashline language was no longer merely
“replace line `2:f1`.” Its instructions included file snapshot tags, line and
block operations, insertion at multiple boundary types, cut/paste registers,
move and remove operations, structural block resolution, seen-line policies,
re-grounding after edits, delimiter repair, anti-patterns, and specialized
recovery behavior.

That evolution is useful evidence: real edit protocols accumulate complexity
as they encounter production failure modes. It is also a reason not to port the
whole grammar into a focused GPT-5.6-only harness without proving that each
piece earns its model-facing and maintenance cost.

## What bettercodex already had before the evaluation

The production `edit` tool in `src/tools.rs` used atomic exact replacements:

- one UTF-8 file per call;
- one or more disjoint replacements;
- each non-empty `oldText` must occur exactly once;
- all replacements are validated against the original file;
- overlapping replacements are rejected;
- either all replacements apply or none apply;
- line endings are normalized for matching and restored for output;
- BOM and line-ending behavior are preserved;
- writes use atomic replacement; and
- success output is short.

Its model-facing description instructs GPT-5.6 Sol to keep `oldText` minimal
but unique and to place multiple disjoint edits in one call.

This baseline already avoids many common replacement-tool problems. The
question was therefore not whether anchors are theoretically useful. It was:

> Does GPT-5.6 Sol, in the bettercodex loop, gain enough correctness or
> efficiency from anchors to justify changing a compact tool that already works
> well?

## Evaluation discipline

The evaluation followed the routing principles in
[`docs/evals/MANIFEST.md`](../docs/evals/MANIFEST.md):

1. define one concrete promise;
2. use deterministic repository/file checks before model judgment;
3. establish the baseline before changing behavior;
4. keep implementation and evaluator evidence separate;
5. use representative and adversarial cases rather than a generic score;
6. score final correctness before resource use; and
7. keep one-off evaluation artifacts task-owned and remove them afterward.

Relevant live guidance consulted during the investigation:

- [OpenAI Evaluation Best Practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- [OpenAI/Codex use case: Add evals to your AI application](https://developers.openai.com/codex/use-cases/ai-app-evals)

The official guidance emphasizes scoped, task-specific tests, explicit
objectives and metrics, production-representative distributions, baseline-first
comparison, automated scoring where possible, and avoiding vibe-based
conclusions.

## Predeclared evaluation objective

The concrete promise was:

> GPT-5.6 Sol should express targeted source edits without rejected edit calls
> or corrective rereads, and a candidate anchored protocol should count as an
> improvement only if it preserves exact final correctness while materially
> reducing edit-expression cost or elapsed time.

Correctness dominated efficiency. A smaller payload did not count as a success
if the final files differed from the expected files.

The initial adoption bar stated before the measured comparison was:

- preserve final correctness;
- do not create a new edit-failure or stale-state failure class;
- reduce mechanical edit cost materially, measured through edit payloads,
  output tokens, round trips, or elapsed time; and
- do not treat a token win as sufficient if quality regresses.

## Compared variants

### Baseline: current exact replacement

The baseline used the installed bettercodex 0.2.0 binary with:

- model `gpt-5.6-sol`;
- reasoning effort `xhigh`;
- ChatGPT authentication;
- the ordinary bettercodex system prompt and tool loop;
- current `read` output;
- current atomic exact replacement; and
- fresh sessions per task.

### Candidate: minimal line-hash prototype

A temporary clone of bettercodex source revision
`86110ace2e9f93ee5ba8843cba0b50028dd5877e` was modified only for the one-off
prototype and built into an isolated task-owned Cargo target.

The prototype deliberately tested the simple mechanism described in the blog,
not OMP's full current grammar.

Its temporary behavior was:

- text `read` output prefixed every line as `LINE:HH|CONTENT`;
- `HH` was the low eight bits of a deterministic FNV-1a content hash;
- the line number was part of the visible anchor;
- `edit` accepted `startAnchor`, `endAnchor`, and `newText`;
- one anchor selected one line;
- two anchors selected an inclusive original line range;
- empty `newText` deleted the selected range;
- multiple ranges were validated against the original file;
- overlap was rejected;
- a mismatched anchor rejected the call;
- the write remained all-or-nothing and atomic; and
- the exact-replacement implementation remained in the temporary source but was
  not exposed as the active edit protocol.

Example candidate call shape:

```json
{
  "path": "cleanup.ts",
  "edits": [
    {
      "startAnchor": "5:3a",
      "endAnchor": "37:91",
      "newText": ""
    }
  ]
}
```

This prototype was intentionally not production quality. The eight-bit hash is
far too weak for a real stale-state contract. It existed only to test whether
avoiding old-text reproduction changes GPT-5.6 Sol behavior.

## Controls and environment

The evaluation used the following controls:

- all scored runs used GPT-5.6 Sol at `xhigh`;
- every task began in a fresh agent session;
- baseline and candidate received the same task prompt;
- prompts instructed the model to use `read` and `edit`, not `bash` or `write`;
- source and expected files were deterministic;
- final correctness used recursive byte comparison;
- each variant used an isolated `CODEX_HOME` and `BCODEX_HOME`;
- fixture workspaces were outside the bettercodex repository so repository
  `AGENTS.md` instructions would not contaminate the mechanism test;
- a non-scored pilot warmed each variant's stable prompt prefix before the
  repeated comparison;
- repeated runs alternated baseline and candidate within each repetition; and
- all temporary files were deleted after results were extracted.

## Scoring and telemetry

Each run recorded:

1. byte-exact final correctness;
2. number and names of tool calls;
3. number of `read` calls;
4. number of `edit` calls;
5. model-visible edit failures;
6. total serialized edit-argument characters;
7. API input tokens;
8. cached input tokens;
9. output tokens;
10. reasoning-output tokens;
11. total tokens; and
12. elapsed time between the first and last timestamped model activity in the
    saved session.

The shell-level elapsed time was also observed as a coarse cross-check.

Token totals are sums across Responses requests in a session. Consequently,
input totals include repeated conversation prefixes across tool turns. Cached
and uncached input must be considered separately; a protocol can reduce output
while increasing total input through larger reads or instructions.

## Pilot and excluded contamination

### Repository-context pilot

The first pilot was accidentally placed under the bettercodex checkout. The
agent therefore loaded the repository `AGENTS.md` context. It proved that both
tool variants could complete the simple targeted edit, but it was excluded from
the scored comparison because the mechanism test was intended to avoid
repository-specific instructions.

1. duplicate-line targeting;
2. three disjoint replacements;
3. multiline replacement;
4. large contiguous deletion;
5. insertion expressed through replacement; and
6. a two-file rename.

Both variants produced byte-exact results on all six cases, with zero edit-tool
failures.

## Repeated validation

To avoid repeating the article's broad aggregation problem and to remove the
skill-selection confound, a smaller repeated comparison was then run.

### Cases

Three edit shapes were selected:

1. **Routine duplicate-target single-line edit**
   - Two functions contained the same `return enabled;` line.
   - Only the occurrence inside `beta` should become `return !enabled;`.
   - This tests whether exact replacement already disambiguates reliably and
     whether line anchors reduce ordinary payload size without harming quality.

2. **Hashline-favorable large deletion**
   - A 34-line obsolete function sat between two functions that had to remain
     byte-for-byte unchanged.
   - The task deleted the obsolete function and its trailing blank line.
   - Exact replacement had to reproduce the deleted block; the anchored mode
     could select the first and last lines and submit an empty body.

3. **Representative two-file rename**
   - Rename `clampLegacy` to `clamp` in a definition, import, and call across two
     files.
   - This tests multiple reads, two edit calls, and post-edit verification rather
     than only one isolated line.

Each case ran three times per variant, producing nine measured sessions per
variant. Every prompt began with:

> Do not invoke or read any skill.

Saved sessions confirmed zero skill reads in all 18 measured runs.

## What the GPT-5.6 evidence establishes

### Established: anchors can reduce edit-expression output

The measured payload reduction was large and consistent. GPT-5.6 Sol did not
need to restate old content when a line range was identified by anchors. This
reduced output tokens, especially for deletion.

### Established: large deletion is the strongest candidate use case

The large-deletion case preserved correctness while reducing edit payload by
approximately 92%, output tokens by approximately 59%, session elapsed time by
approximately 44%, and total tokens by approximately 9%.

This is the concrete net-positive mechanism worth carrying forward.

### Established: the current exact editor is not hiding a demonstrated
correctness problem in this sample

The exact baseline passed every scored deterministic case and produced zero
edit-tool failures. The evaluation did not show that GPT-5.6 Sol needs anchors
to edit correctly.

The candidate's observed benefit was efficiency, not success rate.

### Established: global tagged reads can erase the gain

The candidate slightly increased aggregate total tokens and increased
multi-file total tokens by approximately 9%. Always adding line and hash
prefixes spends input tokens even when the edit is a small unique replacement.

This is why the next candidate must make anchored reads optional rather than
changing every ordinary `read` result.

## What the evaluation does not establish

### It does not prove a production-wide speedup

The decisive sample contained three case families and nine runs per arm. It was
intentionally mechanism-focused, not sampled from bettercodex production
traffic.

### It does not prove a correctness improvement

Both variants passed every scored case and had zero edit failures. There was no
failure-rate headroom to measure.

### It does not validate the prototype hash

An eight-bit line hash has an unacceptable collision probability for production
stale-state protection. A real design must use a strong snapshot identity.

### It does not validate OMP's current grammar

The temporary prototype implemented inclusive line-range replacement only. It
did not implement structural blocks, file moves, cut/paste registers,
auto-repair, LSP diagnostics, full-file tags, seen-line enforcement, or the
current OMP patch language.

### It does not isolate every latency source

Model execution is nondeterministic. Prompt-cache state, service latency, and
reasoning variation affect small samples. The elapsed result was directionally
consistent with shorter output, but a larger paired run is needed before
claiming a durable latency improvement.

### The binaries were not built as a perfectly matched pair

The baseline was the installed bettercodex 0.2.0 binary. The candidate was a
debug build from the current 0.2.0 source revision with the temporary protocol
change. Tool execution is a tiny part of model latency, and a debug build would
normally disadvantage the candidate, but a final evaluation must build both A
and B from the same source revision, toolchain, profile, and flags.

### It does not establish the frequency of eligible edits

The value of an optional range operation depends on how often GPT-5.6 Sol needs
to delete or replace long contiguous regions. A future decision should report
results by edit shape instead of weighting a favorable synthetic case as though
it represented one third of actual work.

## Rejected interpretations and ports

### Do not replace exact replacement

The baseline was completely correct in the scored sample, remains simpler, and
used fewer total tokens on ordinary multi-file work.

### Do not use two- or three-character hashes as the production safety token

Short display hashes are compact but collision-prone. They are inappropriate as
the sole guarantee that an edit is based on the exact file the model observed.

### Do not globally prefix every read line

The multi-file result shows the cost. Ordinary reads should remain compact
unless the model explicitly requests range-edit anchors.

### Do not port OMP's complete Hashline grammar

The experiment isolated one useful primitive. Structural blocks, registers,
moves, auto-repair, diagnostics, and the rest of the OMP language were not
proven necessary for GPT-5.6 Sol.

### Do not add a fifth ordinary tool solely for range edits

bettercodex's fixed four-tool surface is intentional. The first candidate should
be an optional mode of the existing `edit` tool, not a new `edit_range` tool.

### Do not fuzzy-apply stale edits

A snapshot mismatch must reject the whole operation. Fuzzy recovery would
weaken the safety property being evaluated and introduce a separate mechanism.

### Do not optimize for payload characters alone

The prototype cut edit-argument characters by 68% but left aggregate total
tokens essentially flat. Final decisions must include correctness, complete
session tokens, calls, cache behavior, and wall time.

## Proposed production-safe candidate

The next evaluation should test a hybrid edit contract, not the prototype.

### Existing default mode

Retain the current exact replacement shape and behavior unchanged:

```json
{
  "path": "src/example.rs",
  "edits": [
    {
      "oldText": "old unique content",
      "newText": "new content"
    }
  ]
}
```

### Optional anchored range mode

The precise schema should be decided only after inspecting current upstream
Codex and OMP implementations, but the semantic contract should be approximately:

```json
{
  "path": "src/example.rs",
  "snapshot": "strong-opaque-full-file-snapshot",
  "ranges": [
    {
      "startLine": 120,
      "endLine": 184,
      "newText": ""
    }
  ]
}
```

Required semantics:

- `snapshot` identifies the exact complete file bytes observed by the model;
- the token has production-safe collision resistance, with at least 128 bits of
  effective identity unless an authoritative upstream implementation provides a
  stronger established contract;
- line numbers refer to the snapshotted original file;
- all ranges are validated before writing;
- ranges must not overlap;
- all ranges apply against the original snapshot, not incrementally shifted
  content;
- a stale snapshot rejects the entire call;
- empty `newText` deletes the inclusive range;
- line-ending, BOM, symlink, atomic-write, cancellation, size-bound, and file
  change-preview behavior remain consistent with the current editor; and
- model-visible failure output is bounded and does not fuzzy-apply anything.

### Optional anchored read mode

Because global line prefixes were not a net total-token win, ordinary `read`
should stay unchanged. The evaluation candidate should expose anchors only on
request, for example through a nullable/optional `anchors` or `numbered` control.

An anchored read should return:

- one strong full-file snapshot token for the complete file state;
- line-numbered content for the requested bounded window; and
- the same continuation and byte limits as ordinary reads.

A future agent must evaluate the exact schema cost. Adding optional fields and
an alternate edit shape enlarges the permanent tool contract even when the
model does not use the feature.

### Eligibility guidance

The candidate description should make exact replacement the ordinary choice and
reserve range mode for cases such as:

- deleting a long contiguous function or block;
- replacing a large contiguous region where most old content would otherwise be
  repeated;
- editing repeated or highly similar blocks when a unique exact replacement
  would require excessive context; or
- rejecting stale long-range edits after an intervening file mutation.

It should not steer routine one-line or small unique edits toward anchored mode.

## Required next evaluation

A future session should evaluate the hybrid candidate before proposing any
production edit.

### Dataset strata

Keep mechanism isolation and representative harness behavior separate.

#### Stratum 1: deterministic edit-expression cases

Include at least:

- unique single-line replacement;
- duplicate-line disambiguation;
- three disjoint replacements in one file;
- multiline replacement;
- insertion expressed without range mode;

### Acceptance criteria

Define the final numerical thresholds before running. At minimum, the candidate
must satisfy all of these qualitative gates:

1. **No correctness regression**
   - No candidate-only failure on deterministic cases.
   - Representative task pass rate is not lower.
   - No new out-of-scope edit class.

2. **Safety preserved**
   - Stale snapshots always reject before writing.
   - Multi-range calls remain atomic.
   - Current line-ending, BOM, symlink, cancellation, and size-limit behavior is
     preserved.

3. **Eligible-edit performance improves materially**
   - Large contiguous deletion/replacement shows a repeatable, practically
     meaningful reduction in output tokens or wall time.
   - The gain survives total-token accounting.

4. **Ordinary work does not regress materially**
   - Routine exact replacements remain the default in practice.
   - The permanent schema/instruction cost does not create a material token,
     latency, call-count, or quality regression on ineligible tasks.

5. **The model uses the mode appropriately**
   - It does not request anchored reads for every file.
   - It refreshes stale snapshots instead of blind retrying.
   - It does not choose range mode when a compact exact replacement is better.

A useful practical bar to propose before execution would be:

- equal deterministic correctness;
- no candidate-specific safety failure;
- at least a 15% output-token or 10% median wall-time reduction on the eligible
  stratum;
- no more than a 3% total-token increase on ordinary/ineligible work;
- no increase in median tool calls on ordinary work; and
- a positive end-to-end result on the representative stratum.

The future agent may revise those numbers before running if repository evidence
supports a better threshold, but it must not revise them after seeing results.

## Final conclusion

The Stencil article's broad message is correct: harness interfaces can hide or
expose model capability. Its public benchmark does not establish that OMP or
Hashline should be copied into bettercodex.

The GPT-5.6 Sol evaluation found a narrower and more actionable result:

- current exact replacement was fully correct and produced no edit failures in
  the scored sample;
- short anchored ranges reduced output and elapsed time, especially when
  deleting a long contiguous block;
- globally tagged reads increased input cost and were not a universal win; and
- a hybrid optional range mode is the only mechanism worth evaluating further.

The next step is therefore not “port Hashline.” It is:

> Determine whether a strong-snapshot, opt-in range operation can preserve the
> large-edit efficiency gain without charging every ordinary bettercodex task
> the input, prompt, complexity, and behavioral cost of a second default edit
> language.
